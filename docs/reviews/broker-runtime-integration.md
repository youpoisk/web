# Broker runtime integration review — cbd43e3 (+ backend 870f855, bd9b2ee)

Frontend cbd43e3 "feat(auth): connect the site to the first-party broker for login, restore and logout". Backend 870f855 "fix(auth): document fail-safe 409 revocation and harden broker edge cases" (addresses docs/reviews/browser-broker-page-followup.md) and bd9b2ee "test(auth): add local end-to-end HTTP check of the browser authorization flow".

Gate: FAIL. The callback, denial and restore logic is sound and well tested, and no password field or token reaches the site. One high finding blocks: logout does not end the server session in the common case. Two medium findings should be fixed in the same pass. Backend 870f855 resolves follow-up findings A–D with no new issues. bd9b2ee is acceptable, with one low item.

## Findings

1. P1 — session.ts:139-149, runtime.ts:83-87. Logout leaves the server session live once the access token has expired. Access JWTs live 15 minutes (backend internal/platform/access/access.go:37), and the site never renews access (refresh stays broker-only). After 15 minutes on the page, POST /v1/auth/logout returns 401 ("inactive caller", local-development.md:42), so nothing is revoked. The site then forgets locally and returns 'local'. The HttpOnly cookie family stays live until its absolute expiry, and the next «Войти» opens the broker with intent=login. There, run() restores from the cookie and shows "continue as @login" (broker.js:232-237): one click, no password. On a shared computer, «Выйти» therefore does not log the user out. The user-facing message ("Сервер был недоступен, сессия завершится автоматически") is wrong for 401: the server answered, and the session does not end soon. The tests (session.test.mjs logout case with 401) assert this outcome as acceptable. Fix: make logout end the cookie family whatever the bearer state is.
   - Backend (YP-077 session-bound cleanup): add a first-party logout on the API origin, for example intent=logout on /auth/authorize or a broker-page action. It identifies the family from the cookie (hint), revokes it under the Web Lock, and returns redirect_uri?state=…. Revoke only the family the cookie names, so a newer account in another tab is not hit blindly. The site then navigates there whenever bearer logout is not 204, or always.
   - Until that exists: return a distinct outcome for 401 ('expired') and show a truthful message. Better still, do not call it logout: tell the user the account is still signed in on the YouPoisk sign-in page and offer the broker route.
   - Add an auth-e2e check that logout with an expired or invalid bearer leaves the family refreshable. That pins down the gap until the fix lands.

2. P2 — main.tsx:4 (storage: localStorage), flow.ts:35, session.ts:32. The pending PKCE flow is shared across tabs, but the contract says per-tab sessionStorage (docs/api-contract.md:24; "Owns only per-tab PKCE state"). BrowserSession hands one storage port to both the scope reference and PendingFlow. bootAuth (runtime.ts:59-60) cancels any pending flow on a plain load, so opening or reloading any other tab while the user is typing a password on the broker deletes that flow. The returning callback then fails with protocol ("Не удалось завершить вход") after the password was entered. Two tabs restoring at the same time (for example after a browser session restore) cancel each other, and every tab but the last one shows an error. The verifier also outlives the tab in localStorage. Not exploitable (the state stays unpredictable), but it breaks the flow and contradicts the reviewed design. Fix: give BrowserSession a separate `flowStorage` port and pass sessionStorage for PendingFlow, keeping localStorage only for the scope reference if a cross-tab remembered owner is intended. Document the split in api-contract.md, and add a test where two sessions share the scope storage but not the flow storage, and booting one does not cancel the other's flow.

3. P2 — exchange.ts:101 (pending.owner check applied to every intent), session.ts:120-121, runtime.ts:56-66. A cookie for another account locks the site in a permanent error state. The scope is bound to owner X (authenticated or recovering) when the user starts intent=login: /login stays reachable by URL, and the header shows «Войти» after any restore error. If the user then picks "another account" on the broker and signs in as Y, the exchange throws stale_session because pending.owner is X. The cookie is now Y's. Every reload then restores for X, gets a code for Y, throws stale_session and shows the error view. No UI path returns to guest (logout appears only when authenticated), so only signing in as X with a password, or clearing site data, recovers. This fails closed (no data crosses accounts), but it is a lockout. Fix: apply the owner equality check only to intent=restore. A login/register result should commit the new user with a fresh epoch, after clearPrivate, which completeCallback already does for non-restore. For a restore whose result belongs to another user, demote to guest the same way as login_required (fresh epoch, clear, cancel), or commit Y with a fresh epoch, so the next boot does not loop through errors. Add tests for login as Y while X is remembered, and for restore returning Y.

4. P3 — main.tsx:4, session.ts:43-48, runtime.ts:26-27. Configuration and damaged-record failures are fatal and misreported. The main.tsx IIFE turns any constructor failure into null and shows "браузер запрещает хранение данных". A damaged yp.auth.scope.v1 value (protocol) disables sign-in permanently with no reset. A bad VITE_API_ORIGIN (configuration) gets the same storage message. In both cases the boot path never scrubs a ?code=/?error= callback query from the address bar. Separately, authConfig falls back to http://127.0.0.1:18080 and to origin+pathname in every build, so a production build without env navigates users to a loopback broker, or to an unregistered callback (broker 400 page, no way back). Fix: on a protocol error from the constructor, remove the damaged scope key and re-initialise as guest (the record is not authentication). Map the error kind to its message. When no session is available, scrub code/state/error with history.replaceState. Require VITE_API_ORIGIN and VITE_AUTH_CALLBACK when import.meta.env.PROD is set.

5. P3 — session.ts:101 (pre-existing ordering, now on the boot path). completeCallback calls #identity() (a storage read that can throw stale_session/storage) before captureDenied/capture scrub the URL. If it throws, the code/state (or error/state) query stays in the address bar and history. Exposure is small (single-use code, 90 s, PKCE-bound), but it breaks the "scrub before storage reads" rule that flow.ts follows. Fix: call #identity() after the flow capture, or have bootAuth scrub any callback-shaped query on failure.

6. P3 — runtime.ts:43-44 with runtime.ts:59-60. "Обновите страницу, чтобы повторить" after a failed login exchange does not retry. capture() already replaced the URL, and the reload cancels the pending flow, so a login/register user lands on guest and has to press «Войти» again. The broker then offers "continue as", with no password, so no credential is at risk; only the advice is wrong. Restore is unaffected (the remembered owner restores again with a new state, as ADR-0008 intends). Fix: for network/timeout failures, offer a «Повторить вход» action that calls signIn(intent) instead of asking for a reload.

7. Nit — main.tsx:9 (startAuth). No in-flight guard. Two fast submits run two signIn calls, and the second cancels the first's flow. Usually the later assign wins and nothing breaks, but the first call can also surface a stray error toast. Disable the button while redirecting.

8. Low — backend scripts/auth-e2e.mjs:40 and :100. A damaged .artifacts/qa-e2e.json makes JSON.parse throw. V8's SyntaxError message quotes part of the input, and line 100 prints error.message, which can include part of the QA password. Fix: wrap the credential read and print a fixed message such as "credential file unreadable". Optional extra checks: exchange with a wrong verifier, exchange from a foreign Origin, and the expired-bearer logout from finding 1.

## Checked and correct

- captureDenied (flow.ts:128-145) is strict. It accepts only the exact callback origin and path; no userinfo, no hash; exactly one error in {login_required, access_denied} and exactly one canonical state; no other keys (a code next to error is rejected). The URL is scrubbed to origin+path before any storage read, and the return hash is restored only after the state matches the stored flow. completeCallback tries captureDenied before capture, so `error` never reaches the code path, and capture rejects any `error` key anyway.
- CSRF and forced logout: a crafted ?error=login_required&state=X changes nothing unless X equals this browser's pending 256-bit state, which only travels to the API-origin broker (no-referrer). A wrong state throws protocol: one error view, no cancel, no demotion. Demotion needs a live (unexpired, same owner/epoch) restore flow with login_required, and is local only (the cookie family is untouched). Stale or expired refusals just release the flow (tested with +16 min).
- No restore loop: login_required demotes and stops. access_denied keeps the state and stops. Exchange, storage and network failures show an error view without redirecting. Restore runs at most once per page load. StrictMode double effects share the module-level authBoot promise, and the cleanup flag drops a late setState.
- Cancelling a pending flow on a plain load is safe within one tab (Back from the broker, closed broker page). The exact-nonce cancel never touches a replacement flow. The cross-tab problem is finding 2.
- Logout sends the bearer with credentials 'omit', redirect 'error' and a timeout, and forgetLocal runs on every outcome. This is correct for 204. See finding 1 for 401.
- main.tsx: /login and /register have no inputs and submit to the broker, and the copy says credentials go only to the API page. The only remaining password input is the mock /reset-password page. No token is written to localStorage or a URL (the scope record holds only version/owner/epoch). Header and sidebar render the real login/name through React escaping and offer logout. The demo profile is still present; its removal is the next task (WEB-REL-001), so it is not flagged.
- The fetch fix (client.ts, exchange.ts, session.ts) wraps globalThis.fetch so it is no longer called as a method; regression tests call it unbound.
- Backend 870f855: env.AbortSignal is injected and feature-checked; restore with a storage/protocol failure returns login_required instead of a form; a network sign-in failure offers a cookie-based retry; the 409 cross-run revocation is documented as deliberate; web-stop stops only node; the storage message says reload. These resolve follow-up findings A–D.
- Backend bd9b2ee: the script prints only PASS/FAIL names and HTTP statuses (apart from finding 8). The credential file is under .artifacts/, which .gitignore:410 ignores. The gate is a fixed argv. The checks cover cookie attributes, hint origin refusal, attempt retry idempotence, broker callback validation, code issue, CORS exchange, replay refusal, /v1/me, logout revocation and the dead family.
