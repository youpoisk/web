# Site own lists, writes and server card review (YP-051)

Commits: frontend 087fd08 "feat(library): load own library, watch-later and ratings lists from the API", 0631410 "feat(library): toggle watch-later on server list cards with lease and idempotency", 483a23e "feat(catalog): server video card page with rating and watch-later writes"; backend 7992cb0 "chore(dev): gate runner runs reviewed scripts/gates and frontend contract import", 7369e44 "test(library): cover the website write path in the local end-to-end check".
Independent reviewer, source review via device shell. Gate: FAIL.

## Summary

The data layer is sound: the imported contract (25 operations) is byte-identical to backend api/openapi.json at 80ac923/HEAD (sha256 7140b030...), every response goes through the generated validators (url, preview_url, channel url and youtube ids are pattern-restricted to https://www.youtube.com/watch?v=<11>, https://i.ytimg.com/vi/<11>/hqdefault.jpg, https://www.youtube.com/channel/UC<22>), all server strings are rendered as React text nodes, toCard does not invent titles/durations/ratings, revisions are safe integers, and PATCH always carries expected_revision, so no write can be applied twice or over a newer state. StateWriter's 410 handling is correct for the backend (lease invalid/expired on a fresh execution; with a fresh key the "expired receipt" branch of the same 410 reconcile_required cannot occur).

The gate fails on the UI integration: the new server card page is unreachable for the videos that actually exist on the server (the seeded QA data is the demo catalog), so a signed-in user sees contradictory local vs server state; a 409 in the list does a full location.reload, which re-runs the broker restore navigation; and uncertain outcomes are retried with a fresh key, turning the user's own committed write into a "changed on another device" conflict + reload. The gate-runner extension also weakens its own stated safety rule.

## Findings

1. MEDIUM - signed-in viewers never reach the server card for demo-catalog ids; list and card contradict each other. src/main.tsx:22 `current=videos.find(...)` wins over the server page, and the remote effect (src/main.tsx:21, `videos.some(v=>v.id===m[1])` -> setRemote(null)) skips any id in the demo catalog. Backend scripts/qa-seed.mjs seeds the QA account exclusively with demo-catalog ids, and the list cards (src/main.tsx:24) link to `#/video/<id>`. So from «Мои оценки» showing «Ваша оценка: 7» (server) the user lands on the local demo page with «Рейтинг YouPoisk пока не подключён», a local score row («сохраняется только в этом браузере») and a local watch-later button; writes there never reach the server, and the 483a23e rating write path is effectively unused for real data. Fix: for a signed-in viewer (and for guests too, since the public card is readable) load the server card for every /video/<11-char id> and use the demo page only as fallback on 404/error, or merge: render the demo page but take rating/my_state from getVideoCardByYoutube and route writes through StateWriter.

2. MEDIUM - 409 on the list toggle reloads the whole page, which triggers the broker restore round-trip. src/main.tsx:21 serverToggleLater: `if(conflicted(e)){...;location.reload()}`. After reload the remembered scope is 'recovering', bootAuth navigates to the API broker page and back (runtime.ts:83-84), losing pagination/scroll; with the double-click race below, a simple double click causes this. `setServerList(prev=>prev?{...prev}:prev)` before it is dead code. Fix: refetch the current list in place (bump a reload counter in the serverList effect deps, or call loadList for the first page and replace items), as the card page already does with loadCard.

3. MEDIUM - uncertain PATCH outcomes are not retried with the same Idempotency-Key. lists.ts:79 generates a new key per call and StateWriter only retries 410. On network/timeout/503/429 the UI says «Не удалось сохранить. Попробуйте ещё раз.»; the user's retry sends a new key with the same expected_revision. If the first request committed, the server answers 409 (revision moved) and the UI reports «Данные изменились на другом устройстве» and reloads (finding 2) for the user's own write. This is data-safe thanks to expected_revision (no double toggle, no lost update), but it ignores the contract that exists exactly for this case: ADR-0006 and local-development.md:56 - exact retry with the same key is answered from the receipt before lease/version checks (even after lease expiry, within the 10-day receipt) and returns the original result; the request hash excludes key, lease and auth metadata. Fix: in StateWriter keep the last uncertain command per video ({key, expected, change, lease}); on ApiError kinds network/timeout and http 429/503 either retry automatically once (respecting Retry-After) or, when the user repeats the identical command (same videoId, expected, change), reuse the stored key and original lease; drop it on any definitive answer (200/409/410/422). A fresh key after 410 is correct (410 writes no receipt) - keep that, optionally also checking error.code==='reconcile_required'. Add a unit test for "network error then identical retry reuses key".

4. LOW - no in-flight guard for writes; double clicks produce false conflicts. serverToggleLater and remoteWrite (src/main.tsx:21) use the revision captured at render; two clicks before re-render send two PATCHes with the same expected_revision, the second gets 409 (list: full reload; card: misleading "другое устройство" toast). Concurrent first writes also issue two leases because #anchor caches the value, not the promise (lists.ts:69-71). Fix: per-uuid pending set (disable the button / ignore while pending), cache the lease promise in #anchor (reset to null on rejection).

5. LOW - public card page fails for a viewer whose scope is still 'recovering'. The remote effect (src/main.tsx:21) only waits for 'loading'/'redirecting'. When boot ends in status 'error' (e.g. broker unreachable) the remembered scope stays 'recovering' and ApiClient refuses even optional-auth getVideoCardByYoutube (client.ts:99), so a public card shows «Не удалось загрузить видео» although a guest could read it. Fix: use a separate guest ApiClient (session: ()=>({state:'guest'})) for card reads when authView is not 'authenticated'; my_state is not rendered then anyway (`own=signedIn?c.my_state:undefined`).

6. LOW - server list UI shows controls and numbers that do not apply. src/main.tsx:40 shows the category/sort/search filters above server lists but serverList ignores them; poster() renders `0{videos.indexOf(v)+1}` = «00» for every server card (src/main.tsx:23); the channel link for a card with null channel points to `#/channel/` (empty name); the sidebar «Посмотрю позже» counter (src/main.tsx:30) still counts local demo ids for a signed-in viewer. Fix: hide filters (or apply them client-side) for serverList, omit poster-number for server cards, render the channel as text when name is empty, take the counter from the server list or hide it when signed in.

7. LOW - loadMore has no in-flight/generation guard (src/main.tsx:21). Double click appends the same page twice (duplicate React keys); a slow page from an earlier visit of the same route kind can append to a refreshed list. Fix: store a request generation/abort controller with serverList and a `loadingMore` flag.

8. MEDIUM (backend 7992cb0) - gate runner now executes any scripts/gates/<name>.ps1 present in the working tree. scripts/gate-runner.ps1:75-80 accepts a regex-checked name (no traversal possible: ^[a-z0-9-]{1,40}$, fixed directory, Test-Path -PathType Leaf) and runs it with ExecutionPolicy Bypass on the host. The comment says "reviewed repository script", but nothing enforces review: an untracked or locally modified file runs just the same, and once registered it stays in $gates for the runner's lifetime. This contradicts the header promise (lines 3-5: "File content is never executed: unknown names are rejected") whose purpose is to let an assistant without host access trigger only fixed gates. (Existing gates such as auth-e2e and frontend already run working-tree code, so the boundary was not airtight, but this makes arbitrary host PowerShell a one-file step.) Fix: before registering, require `git ls-files --error-unmatch scripts/gates/<name>.ps1` and `git diff --quiet HEAD -- scripts/gates/<name>.ps1` (and no untracked status), re-check on every run instead of caching, and update the header comment to describe the rule honestly.

9. LOW (backend 7369e44) - auth-e2e grows the global catalog and the QA library every run. scripts/auth-e2e.mjs:105 creates a new random 'E2eList' + 4 chars YouTube id per run; POST /v1/me/videos writes a global catalog row (shared, will be visible in future catalog listing/search) and leaves the video in the QA account's library (only later is removed). On the local development DB this is tolerable but accumulates indefinitely and pollutes the QA account the site is demoed with. Fix: use one reserved fixed id (e.g. 'E2eQaVideo0'), read its card first for the current revision (already done), and end by PATCH added=false/later=false; also add the two contract cases the frontend relies on: exact retry with the same key returns the original 200 result, and a fresh execution without/with a damaged X-Offline-Lease returns 410 reconcile_required.
