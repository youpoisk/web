## Спорные вопросы

DEC-WEB-001 — Вопрос: как синхронизировать два отдельных репозитория без незаявленного доступа CI к private backend? Выбор: коммитить зеркало IDL, SHA256 по LF, полный backend commit и сгенерированные типы; CI/build проверяют целостность и воспроизводимость. При совместных изменениях api:check-source сравнивает соседний checkout; импорт разрешен только из закоммиченного backend-контракта. Причина: frontend build воспроизводим без сетевой зависимости от движущейся backend-ветки. Независимый межрепозиторный CI trigger/artifact остается выпускным улучшением, его работа не имитируется.

DEC-WEB-002 — Вопрос: считать ли наличие типов подключением сайта к серверу? Выбор: нет, текущий UI остается демонстрационным до fetch/auth/query интеграции. Никаких новых runtime credential storage/cookie workaround в задаче типов. Причина: генерация контрактов не доказывает безопасный transport при blocked third-party cookies.
DEC-WEB-003 — Вопрос review: достаточно ли git diff для provenance? Выбор: дополнительно читать точный HEAD:api/openapi.json и сверять содержимое до записи; отсутствие tracked файла отклонять. До генератора разрешать только внутренние $ref/$dynamicRef и запретить $id rebinding. Причина: непроиндексированный файл не должен приписываться чужому коммиту, генерация не должна читать произвольные файлы/сетевые схемы.
DEC-WEB-004 — Вопрос: как проверять wire JSON без eval в MV3? Выбор: Ajv2020 standalone компиляция из общего IDL на этапе сборки, bundle browser helpers через esbuild, generated artifacts и drift gate. Причина: TypeScript не проверяет серверный JSON во время выполнения; runtime new Function нарушил бы CSP расширения. Схемы не дублируются вручную. Safe-integer и account context проверки останутся обязанностью transport.
DEC-WEB-005 — Вопрос review: как совместить Unicode email и schema validation? Выбор: исправить канонический backend IDL вместо запрета уже поддерживаемых адресов; сохранить ограничения wire envelope и полную валидацию DTO, семантику регистрации проверяет net/mail на сервере. Причина: легальный пользователь не должен терять вход/профиль из-за несовместимого стандартного format=email.
DEC-WEB-006 — Вопрос: должен ли базовый fetch-клиент самостоятельно запускать cross-site refresh? Выбор: нет; business transport получает memory session provider и возвращает401/503 без неявной авторизации или повторной записи. Cookie-changing auth operations исключены, отдельный broker/coordinator обеспечит прозрачное recovery и один повтор исходной команды. Причина: непротестированная third-party cookie схема не должна создавать reuse/потерю очереди, а смена owner/epoch должна отбрасывать поздние ответы.
DEC-WEB-007 — Вопрос review: достаточно ли strict UTF8 декодирования ответа? Выбор: дополнительно проверять scalar Unicode строк и ключей JSON, поскольку escape последовательности lone surrogates проходят JSON.parse и не являются корректными Unicode значениями. Причина: клиент не должен принимать или ставить в очередь payload, который строгий серверный decoder отвергнет. Валидные emoji/символ замены не запрещены.
DEC-WEB-008 — Вопрос: включать ли новые browser grant endpoints в обычный типизированный business-клиент? Выбор: генерировать общий контракт/валидаторы, но исключить Issue/Exchange из genericApiClient и в типах, и доfetch. Отдельный authcoordinator должен проверять pendingstate/accountgeneration и не принимать позднюю авторизацию другого аккаунта. Причина: wireтипы не заменяют безопасность browserflow; бизнес-запросы не должны смешивать bearer/cookie/codeканалы. Type-onlynegativechecks входят в build.

DEC-WEB-009 — Вопрос: может ли обычный fetch-клиент выполнять nativecookiehint? Выбор: нет, generatedDTO присутствует дляauthcoordinator, но genericAPIClient исключает identifyBrowserSession втипах/доfetch при любомaccountstate. Причина: егоcredentials:omit/memoryBearer канал не равенHttpOnlynativecookie; смешивание нарушитrecoverableflow. Referrerpolicy=no-referrer установлендоresource links длябудущегоcodecallback.
DEC-WEB-010 — Вопрос: где хранить frontendPKCE и когда убирать code изURL? Выбор: per-tab sessionStorage port с namespace APIorigin+exactcallback, state/verifier32cryptoBytes, S256, срок15мин; code/state убираются до чтенияstorage/валидации. Owner+epoch фиксируются доasyncdigest и проверяются приcallback, pending удаляется только послеуспешногоexchange/identitychecks; explicitcancel можетосвободитьexpired/staleflow поточномуматчуnonce. Причина: latecallback и двойнойclick не должныпереключатьаккаунт/перезаписыватьproof; ниrefresh, ниaccess, нипароль не относятсяк pendingflow. Потеряответаexchange потребуетновогоflowчерезживуюAPIcookie, незапросапароля.
DEC-WEB-011 — Вопросreview: какосвободитьinterruptedflow послеобычногорелоада безnonceвURL? Выбор: pendingSummary сминимальнымиmetadata/status безverifier/challenge, затемявныйcancel поточномуnonce; новыйbegin незатираетстарый автоматически. Причина: coordinatorдолженуметьперезапуститьexpired/staleпереход, нечитаяприватныеstoragekeys и неотменячужойновыйflow.


DEC-WEB-012 — Вопрос: выдавать ли текущую форму-макет за настоящую авторизацию? Выбор: гость по умолчанию, отдельная явно обозначенная кнопка «Открыть демопрофиль», состояние только в памяти и явный выход в гостевой каталог. Причина: серверный auth coordinator ещё не подключён; пароль из макета не должен создавать впечатление успешного входа. Реальная регистрация, вход, отзыв сессий и изоляция серверных данных остаются открытыми WEB-004/005. Гостевые оценки/список просмотра остаются локальными; автоматический импорт не выполняется.
